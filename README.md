# oascmd

Turn an OpenAPI 3.0/3.1 document into a Cobra command tree — at **runtime**
(parse a spec, get `[]*cobra.Command` back) or at **build time** (generate
strongly-typed Go source you compile).

```
module github.com/d3servelabs/openapi-commands   (Go 1.23.5)
```

## Why

A REST API already describes its own surface: paths, methods, parameters,
request bodies, enums, defaults. Hand-writing a CLI on top of that duplicates
every one of those facts and lets them drift. `oascmd` derives the command
tree from the spec instead, so `namefi dns records get --domain x.eth` is a
consequence of the OpenAPI document rather than a parallel implementation of
it.

The motivating consumer is the Namefi backend, which serves an oRPC-generated
OpenAPI 3.1 document at `/v-next/openapi/doc.json`; the library itself is
generic and knows nothing about Namefi.

## Layout

```
oascmd.go        the normalized Operation model (shared by both modes)
body.go          request-body envelope resolution (wrap / unwrap)
naming.go        command-path derivation + flag-name rules
exec.go          request building, auth hook, execution, output printing
hooks.go         the Hooks surface, SkipOperation, confirmation prompt
validate.go      enum validation shared with generated code
spec/            OpenAPI parsing (libopenapi) -> the normalized model
runtime/         spec -> []*cobra.Command, dynamically
gen/             spec -> Go source (typed structs + command constructors)
gen/goldenpkg/   checked-in generated output, compiled + golden-diffed by tests
lock/            the lock file: snapshot, severity-classified diff, policies
cmd/oascmd-gen/  the generator CLI, for go:generate
examples/petstore/  a runnable CLI wiring up both modes
testdata/        the fixture spec exercising every supported feature
```

## Quickstart: runtime mode

```go
import (
    "github.com/d3servelabs/openapi-commands"
    oasruntime "github.com/d3servelabs/openapi-commands/runtime"
)

root := &cobra.Command{Use: "myapi"}
err := oasruntime.Attach(root, specBytes, oasruntime.Options{
    Exec: oascmd.ExecOptions{
        BaseURL: "https://api.example.com",
        Auth: func(req *http.Request) error {
            req.Header.Set("Authorization", "Bearer "+token)
            return nil
        },
    },
})
```

`Build` returns the commands instead of attaching them;
`BuildFromOperations` takes an already-normalized `[]oascmd.Operation` if you
source the model yourself.

## Quickstart: buildtime mode

```go
//go:generate go run github.com/d3servelabs/openapi-commands/cmd/oascmd-gen -spec api.yaml -package apicli -out zz_generated.go
```

The emitted file contains:

- a Go struct per object schema under `components.schemas` (typed fields,
  `json` tags, `*Ref` pointers for `$ref` properties, `json.RawMessage` for
  shapes that are not statically representable),
- one `New<Path>Command(exec oascmd.ExecOptions) *cobra.Command` constructor
  per operation, with typed flag variables and inline enum checks,
- `NewCommandTree(exec)` returning the assembled group tree.

Generated output carries `// Code generated by oascmd-gen. DO NOT EDIT.`, is
run through `go/format`, and is compiled by the test suite.

It also writes `oascmd.lock.json` beside the generated file, recording the
CLI surface so a later run can report exactly what changed and refuse to
break existing commands silently. See [The lock file](#the-lock-file).

For programmatic use (custom hooks), call `gen.Generate(specData, gen.Options{…})`
directly instead of the CLI, or `gen.GenerateWithModels` when you also want
the post-hook models the lock is computed from.

## Buildtime vs runtime

|                        | Runtime | Buildtime |
|---|---|---|
| Spec read              | at process start | at generation time |
| Type safety            | **none** — see below | full: the Go compiler checks flags, structs, and call sites |
| Spec changes           | picked up automatically on the next run | require re-running the generator |
| Binary self-sufficiency| needs the spec (embed it or fetch it) | none, the spec is baked in |
| Startup cost           | parse + build the tree every run | zero |
| Response types         | untyped JSON printed as-is | structs available for the caller to unmarshal into |
| Custom per-op code     | via hooks only | hooks plus ordinary Go around the constructors |

**The type-safety point.** Runtime mode has *no compile-time type safety*: a
flag's type, its required-ness, and its enum membership are known only from
the schema, so every check is a runtime check performed just before the
request is sent (`required flag --domain not set`, `invalid value "nope" for
--status`). If the spec is wrong or changes shape, you learn at execution
time. Buildtime mode moves those facts into the Go type system: a typed
`int64` flag variable, a `Pet` struct with real fields, a constructor whose
signature breaks the build if the API changed under you. Runtime mode is the
right default for a CLI that must track a moving API; buildtime mode is the
right default for a shipped binary.

Both modes share the same model, naming rules, extension handling, and
executor, so a command behaves identically either way (the example CLI shows
the same operations under both).

## What you can configure

Three questions this library gets asked, and where each answer lives.

**1. The HTTP client — auth, headers, cookies.** All on `oascmd.ExecOptions`,
which both modes accept (`runtime.Options.Exec`, and the argument to every
generated constructor).

| Field | What it does |
|---|---|
| `Client *http.Client` | Your client, so you control timeouts, proxies, TLS and transport. `http.DefaultClient` when nil. |
| `CookieJar http.CookieJar` | Installed on a **copy** of `Client` (your client is never mutated) when it has no jar of its own. |
| `Headers http.Header` | Static default headers on every request. They win over the executor's own `Accept`/`Content-Type`. |
| `Cookies []*http.Cookie` | Explicit cookies attached to every request, in addition to the jar. |
| `Auth AuthFunc` | Called on every request after headers and cookies. |
| `OnBeforeExecute` | Per-request mutation: headers, URL, body (see the hooks matrix). |

Auth helpers cover the common shapes; `AuthFunc` is just
`func(*http.Request) error`, so anything else is a closure:

```go
oascmd.ExecOptions{
    BaseURL:   "https://api.example.com",
    Client:    &http.Client{Timeout: 10 * time.Second},
    CookieJar: jar,
    Headers:   http.Header{"X-Client": {"mycli/1.2"}},
    Cookies:   []*http.Cookie{{Name: "tenant", Value: "acme"}},
    Auth: oascmd.ChainAuth(
        oascmd.BearerAuth(token),              // Authorization: Bearer …
        oascmd.APIKeyAuth("X-API-Key", key),   // any named header
        // oascmd.BasicAuth(user, pass)        // Authorization: Basic …
        func(req *http.Request) error {        // anything else
            req.Header.Set("X-Signature", sign(req))
            return nil
        },
    ),
}
```

**2. Body envelopes.** Wrapped bodies are unwrapped so the flags are the
inner ones. See [Body envelopes](#body-envelopes-wrapping-and-unwrapping).

**3. Request/response lifecycle.** `OnBeforeExecute`, `OnAfterExecute` and
`OnRequestError` on `ExecOptions`, all firing in both modes. See the
[hooks matrix](#hooks).

## Derivation rules

### Command path

Given the tags, `operationId`, method, and path of an operation:

1. **Group words** — `x-cli-group` when set (split on spaces); otherwise the
   first tag, split into words and kebab-cased. No tag and no `x-cli-group`
   means no group: the command attaches to the parent directly.
2. **Leaf words** — `x-cli-name` when set: split on spaces, the last word is
   the leaf command and any preceding words extend the groups. Otherwise the
   `operationId` is split into words (camelCase, digits, `_`, `-`, `.`, and
   spaces are boundaries; acronym runs stay together, so `getHTTPStatus` →
   `get http status`). Leading words that repeat the group words are dropped,
   comparing case-insensitively and ignoring a trailing `s`. The next word
   becomes the **verb** (the leaf command); the rest become resource words
   that extend the groups.
3. **No `operationId`** — the verb is the lower-cased HTTP method and the
   resource words are the static path segments (path parameters skipped),
   each kebab-cased and deduplicated against the group the same way.

The resulting path is `groups + resource words + verb`:

| tag | operationId | method + path | command |
|---|---|---|---|
| `dns` | `getDnsRecords` | `GET /dns/records` | `dns records get` |
| `pets` | `listPets` | `GET /pets` | `pets list` |
| `pets` | `createPet` | `POST /pets` | `pets create` |
| `legacy` | `legacyPing` | `GET /legacy/ping` | `legacy ping` |
| `pets` | *(none)* | `PUT /pets/{petId}` | `pets put` |
| *(none)* | *(none)* | `PUT /untagged/anon` | `untagged anon put` |

Override the whole rule with `Options.NameFunc` (both modes), which takes an
`oascmd.Operation` and returns an `oascmd.CommandPath`.

### Flags

- **Path and query parameters** become flags. The flag name is the parameter
  name kebab-cased, unless `x-cli-flag-name` overrides it. Header and cookie
  parameters are **not** mapped.
- **Types**: `string` → string, `integer` → int64, `number` → float64,
  `boolean` → bool, `array` of any of those → the matching slice flag
  (repeat the flag for multiple values). Nested arrays, unions, and object
  parameters are rejected. OpenAPI 3.1 `["string","null"]` unions are
  accepted and treated as the non-null type.
- **Required** parameters (and all path parameters) become required flags.
- **Enums** are validated before the request is sent, and listed in the flag
  usage string.
- **Defaults** from the schema become the flag default, and such parameters
  are always sent even when the user does not pass the flag.
- **Request bodies** (`application/json` only) always get a `--data` flag
  taking raw JSON. When the body schema is a *flat* object — every top-level
  property is a scalar or an array of scalars — each property also gets its
  own typed flag. `--data` wins when both are supplied. Non-flat bodies get
  only `--data`.
- Every command gets `--json` (print the response body raw instead of
  pretty-printed). Operations marked `x-cli-confirm` also get `--yes`.

### Body envelopes (wrapping and unwrapping)

Some APIs wrap the request body in an envelope: `{"json": {…}}`,
`{"payload": {…}}`, `{"data": {"attributes": {…}}}`. Flags named
`--payload.arg1` would be miserable to type, so `oascmd` **unwraps** the
envelope: the flags are the inner properties (`--arg1 --arg2`) and the CLI
re-wraps them when it builds the request. `--data` still takes the whole raw
body, envelope included.

Three ways to declare it, checked in this order:

1. **Automatic.** While the body has *exactly one* property and that
   property is an object, it is treated as an envelope and descended into.
   `{"json": {"petId": …}}` gives `--pet-id`; `{"json": {…}, "meta": …}` is
   ambiguous, so nothing is unwrapped.
2. **Declared in the spec**, on the request body (or its schema):
   `x-cli-body-unwrap: payload`, dotted for several levels
   (`data.attributes`). `x-cli-body-unwrap: none` (or `false`) turns
   automatic detection off; `auto` (or `true`) is the default.
   `x-cli-body-wrap: envelope` is the inverse — it nests the assembled body
   under a wrapper the spec does **not** describe.
3. **Programmatically**, for specs you cannot edit: the `OnResolveBody` hook
   runs just before resolution and sets the same two fields.

```go
Hooks: oascmd.Hooks{
    OnResolveBody: func(op *oascmd.Operation) error {
        if op.ID == "createPet" {
            op.Body.Ext.Wrap = "payload"      // send {"payload": {…}}
            // op.Body.Ext.Unwrap = "payload" // or flatten an existing one
        }
        return nil
    },
},
```

The precise rules:

- **Order.** `x-cli-body-wrap` supplies the outermost segments; the unwrapped
  envelope path is appended inside it. Both together give
  `{"envelope": {"json": {…flags…}}}`.
- **Depth.** Automatic detection descends as far as the single-object-property
  chain goes; an explicit path may name any depth.
- **Errors, not surprises.** An explicit path naming a property that does not
  exist, or that is not an object, is a build error.
- **Collisions.** If two properties end up deriving the same flag name after
  unwrapping (`petId` and `pet_id` both give `--pet-id`), the build fails
  with a message naming both. Fix it with `x-cli-flag-name` on one of them,
  or turn unwrapping off with `x-cli-body-unwrap: none`.
- **Leftovers.** If a resolved property is still a nested object, the body is
  not flat: the command gets `--data` only, as before.
- **Both modes, one rule.** Runtime and buildtime resolve bodies with the same
  `oascmd.ResolveBody`, so the flags and the submitted JSON are identical.
- **The lock records the effective surface.** `body.wrap` holds the envelope
  path and the flags are the post-unwrap ones, so drift detection describes
  what a user actually types. Changing the envelope is **breaking**: the same
  flags now land somewhere else in the payload.

```yaml
/orders:
  post:
    operationId: createOrder
    requestBody:
      content:
        application/json:
          schema:
            type: object
            properties:
              json:                        # auto-detected envelope
                type: object
                properties:
                  petId: { type: string }
                  quantity: { type: integer }
```

```sh
myapi orders create --pet-id p1 --quantity 2
# POST /orders  {"json":{"petId":"p1","quantity":2}}
```

### Execution and output

The request is built against `ExecOptions.BaseURL`, path parameters are
URL-escaped into the path template, query values are appended, and a JSON
body is sent with `Content-Type: application/json`. `ExecOptions.Auth` is
called on every request. Successful responses are pretty-printed JSON by
default (raw with `--json`, passed through unchanged when not JSON). Non-2xx
responses return an `*oascmd.StatusError` carrying the status and a body
snippet capped at 512 bytes.

## OpenAPI extensions (`x-cli-*`)

| Extension | Where | Effect |
|---|---|---|
| `x-cli-name` | operation | Overrides the derived leaf name. Space-separated words nest: `renamed thing` makes `… renamed thing`. |
| `x-cli-group` | operation | Overrides the tag-derived group. Space-separated words nest. |
| `x-cli-hidden` | operation | Sets `cmd.Hidden`: the command works but is omitted from help. |
| `x-cli-skip` | operation | Drops the operation entirely, in both modes. |
| `x-cli-skip` | parameter | Drops the parameter instead of mapping it to a flag. The escape hatch for a parameter with no flag form, such as an object-typed query parameter whose fields are already exposed individually; without it that one parameter fails the whole generation. |
| `x-cli-confirm` | operation | Prompts `[y/N]` before executing; `--yes` skips the prompt. For destructive operations. |
| `x-cli-body-unwrap` | request body | Names the envelope property whose inner properties become the flags (`payload`, `data.attributes`). `none`/`false` disables automatic detection; `auto`/`true` is the default. |
| `x-cli-body-wrap` | request body | Nests the assembled body under an envelope the spec does not describe (dotted for several levels). |
| `x-cli-flag-name` | parameter / body property | Overrides the derived flag name. |
| `x-cli-shorthand` | parameter / body property | Adds a one-letter shorthand (`-l`). |

Example:

```yaml
paths:
  /pets/{petId}:
    delete:
      operationId: deletePet
      tags: [pets]
      x-cli-confirm: true          # prompt before deleting
      responses: { "204": { description: Deleted } }
  /pets:
    get:
      operationId: listPets
      tags: [pets]
      parameters:
        - name: verbose
          in: query
          x-cli-flag-name: long    # --long, not --verbose
          x-cli-shorthand: l       # also -l
          schema: { type: boolean }
  /internal/debug:
    get:
      operationId: debugDump
      tags: [internal]
      x-cli-hidden: true           # usable but not advertised
      responses: { "200": { description: OK } }
  /renamed:
    get:
      operationId: someWeirdInternalName
      x-cli-group: tools           # -> "tools renamed thing"
      x-cli-name: renamed thing
      responses: { "200": { description: OK } }
```

Extensions are declarative and travel with the spec, so an API team controls
its own CLI surface without the CLI depending on them. Hooks (below) are for
things the spec cannot express.

## Hooks

`oascmd.Hooks` is accepted by both `runtime.Options` and `gen.Options`.

| Hook | Signature | Runtime | Buildtime | Purpose |
|---|---|---|---|---|
| `OnReadOperation` | `func(op *Operation) error` | ✅ | ✅ | Filter or transform operations as read from the spec. Mutate `op` in place; return `oascmd.SkipOperation` to drop it; any other error aborts. |
| `OnBeforeCreateCommand` | `func(op Operation, cmd *cobra.Command) error` | ✅ | ➖ | Runs after the command is constructed, before flags are registered. Mutate `cmd`, or return `SkipOperation` to veto it. |
| `OnAfterCreateCommand` | `func(op Operation, cmd *cobra.Command) error` | ✅ | ➖ | Runs after the command is fully built (flags + `RunE`). |
| `gen.Options.OnEmitOperation` | `func(cmd *gen.CommandModel) error` | ➖ | ✅ | The buildtime analogue of the create hooks: rename the emitted constructor, relocate the command, or veto with `SkipOperation`. Commands do not exist yet at generation time, so `*cobra.Command` cannot be handed to you. |
| `OnResolveBody` | `func(op *Operation) error` | ✅ | ✅ | Runs per operation with a body, after `OnReadOperation` and before envelope resolution. Set `op.Body.Ext.Unwrap` / `.Wrap` for specs you cannot edit. |
| `ExecOptions.OnBeforeExecute` | `[]func(ctx, *http.Request) error` | ✅ | ✅ | Runs after headers, cookies and auth, before the request is sent. **May mutate** the request (headers, URL, and the body via `oascmd.SetRequestBody`) or abort by returning an error. |
| `ExecOptions.OnAfterExecute` | `[]func(ctx, *http.Response) error` | ✅ | ✅ | Runs when the response arrives, before the body is read, the status is checked, and anything is printed. **May inspect and transform** the response (including replacing `resp.Body`) or abort. Fires for non-2xx responses too. |
| `ExecOptions.OnRequestError` | `func(ctx, *http.Request, attempt int, err error) (retry bool, err error)` | ✅ | ✅ | Runs when the transport fails (no response: DNS, connection, timeout). Return `retry=true` to re-send (the body is replayed), an error to abort with it, or `(false, nil)` to surface the transport error. Capped at 100 attempts. |

**Execution order**, precisely:

```
build request
  -> ExecOptions.Headers        (overwrite, so they win over Accept/Content-Type)
  -> ExecOptions.Cookies
  -> Auth
  -> OnBeforeExecute[0..n]      in declaration order; any error aborts
  -> send  --- transport error --> OnRequestError -> (retry: back to send)
       |
       response
  -> OnAfterExecute[0..n]       in declaration order; any error aborts
  -> status check (non-2xx -> *StatusError)
  -> print
```

Every hook that returns an error aborts the run with it, so any of them can
veto. Mutating a request body from a hook must go through
`oascmd.SetRequestBody`, which keeps the request replayable for retries.

The execute hooks live on `ExecOptions`, which generated constructors accept,
so they apply to generated commands too. Per-command customization in
buildtime mode otherwise happens in ordinary Go at the call site: the
generated constructors return plain `*cobra.Command` values you are free to
mutate.

```go
opts := oasruntime.Options{
    Hooks: oascmd.Hooks{
        OnReadOperation: func(op *oascmd.Operation) error {
            if op.Deprecated {
                return oascmd.SkipOperation   // keep deprecated ops out of the CLI
            }
            return nil
        },
        OnAfterCreateCommand: func(op oascmd.Operation, cmd *cobra.Command) error {
            cmd.Annotations = map[string]string{"route": op.Method + " " + op.Path}
            return nil
        },
    },
}
```

## The lock file

The generator records what it produced in `oascmd.lock.json`, written next to
the generated file. On the next run it recomputes the surface, compares it to
the lock, classifies the difference **by severity**, and decides what to do.

Two things it buys you:

- **A reviewable diff.** The lock is the CLI surface in plain JSON — one
  entry per operation with its command words, constructor name, flags, types,
  enums, defaults and body shape. A pull request that changes the spec shows
  exactly how the CLI changed, without anyone reading generated Go.
- **A CI gate.** `-on-drift check` fails the build when the checked-in
  generated code no longer matches the spec, and plain `-diff` prints why.

Commit the lock file. Opt out entirely with `-no-lock`.

```
oascmd-gen -spec api.yaml -package apicli -out zz_generated.go     # keeps the lock
oascmd-gen ... -lock path/to/other.lock.json                       # elsewhere
oascmd-gen ... -no-lock                                            # no lock at all
oascmd-gen ... -diff                                               # report, write nothing
oascmd-gen ... -diff -json                                         # same, for CI
```

### What is in it

```json
{
  "lockVersion": 1,
  "generatorVersion": "oascmd-gen/1",
  "specDigest": "43d8…",
  "operations": {
    "listPets": {
      "operationId": "listPets",
      "method": "GET",
      "path": "/pets",
      "command": "pets list",
      "funcName": "NewPetsListCommand",
      "summary": "List pets",
      "flags": [
        { "name": "limit", "source": "query", "type": "int" }
      ],
      "ext": {},
      "digest": "2cb21072474306fb"
    }
  }
}
```

Operations are keyed by the `operationId` when the spec has one, else
`"METHOD path"` — a stable identity that survives renaming the command. Each
entry carries a `digest` so a diff can jump straight to the changed
operations, and the file as a whole carries a `specDigest` over the
normalized surface (not the raw bytes, so reformatting the YAML is not
drift). `generatorVersion` is recorded too, so a change to the emitter is
itself detectable drift even when the spec stood still.

The file is deterministic: sorted keys, 2-space indent, trailing newline.
Generating twice produces byte-identical output.

**Computed after the hooks.** `OnReadOperation` and `OnEmitOperation` can
skip, rename and mutate operations, so the lock is computed from the
post-hook models. It describes what was actually generated, not what the spec
said. (`TestLockComputedFromPostHookModel` pins this.)

### Why there is no `generatedAt`

A timestamp would change on every run, so every regeneration would produce a
diff even when the CLI surface is identical — the exact noise this file
exists to remove, and enough to make "did anything really change?" unanswerable
at a glance and to cause pointless merge conflicts. The lock records *what*
was generated; git already records *when*. It is deliberately absent, and a
test asserts it stays absent.

### Severity ladder

Every difference is classified, per field, then aggregated per operation and
for the run as a whole. The ladder is ordered
`none < cosmetic < additive < breaking`.

| Severity | Meaning | Rules |
|---|---|---|
| `none` | Identical. | — |
| `cosmetic` | Help text only. Nothing a user types or compiles changes. | summary changed, description changed, flag description changed, `x-cli-hidden` toggled, deprecation notice dropped, enum values reordered |
| `additive` | The surface grew; every existing invocation still works. | operation added, optional flag added, enum value added, optional body added, required flag became optional, shorthand added where there was none, `x-cli-confirm` removed, deprecation added, generator version changed |
| `breaking` | An existing invocation or a compiling caller stops working. | operation removed, command path renamed or moved, constructor renamed, HTTP method or path changed, flag removed, flag type changed, flag moved between path/query/body, optional became required, required flag added, enum value removed, flag default changed, shorthand changed or removed, body removed, body shape changed (flat ↔ `--data`), body became required, `x-cli-confirm` added |

Two rulings worth explaining:

- **A changed default is breaking.** Leaving the flag off now sends a
  different value, so a script that never mentioned the flag silently changes
  behavior — the worst kind of break, because nothing errors.
- **Adding `x-cli-confirm` is breaking.** The command starts prompting, so
  unattended scripts hang unless they learn to pass `--yes`.

### Drift policies

`-on-drift <policy>`:

| Policy | Behavior |
|---|---|
| `auto` (default) | Regenerate when the drift is at most `additive`. On `breaking`, write nothing and print exactly what breaks and how to proceed. |
| `all` | Always regenerate, breaking changes included. The escape hatch when the break is intended. |
| `additive-only` | Apply the safe changes and keep every breaking operation exactly as it was last generated, reporting what was left alone. |
| `check` | Never write. CI mode. |

`additive-only` really does keep the old command: the operation is re-emitted
from its lock entry, so a removed operation stays available and a flag whose
type changed keeps its old type until someone decides otherwise.

### Exit codes

Modelled on `terraform plan -detailed-exitcode` and `gofmt -l`: success is
`0`, real failure is `1`, and "there is drift" gets its own code so CI can
branch on it.

| Code | Meaning |
|---|---|
| `0` | Up to date, or the changes were applied. |
| `1` | Usage or internal error (bad flags, unreadable spec, unparsable lock). |
| `2` | Drift detected and nothing written (`-on-drift check` or `-diff`). |
| `3` | Breaking drift refused (policy `auto`). |

A CI job that must never drift:

```sh
oascmd-gen -spec api.yaml -package apicli -out zz_generated.go -on-drift check
```

### The report

```
Drift detected (overall severity: breaking)

Breaking changes (1):
  ~ pets list  (GET /pets)
      flag --limit type: int -> string (breaking) - the value is parsed differently now; values that used to be accepted may be rejected

Safe additions (1):
  + owners list  (GET /owners)
      operation: added owners list (additive) - new command; nothing that works today stops working
```

`+` added, `~` changed, `-` removed. `-json` renders the same report with a
stable schema (`severity`, `generatorChanged`, `operations[].changes[]`) for
CI to consume; it is golden-tested.

### Library API

The CLI is a thin wrapper; the package is the real interface.

```go
import "github.com/d3servelabs/openapi-commands/lock"

source, models, err := gen.GenerateWithModels(specData, opts)  // post-hook models
next := lock.Compute(gen.LockModels(models))

previous, existed, err := lock.Load("oascmd.lock.json")
report := lock.Diff(previous, next)
switch report.Severity() {
case lock.SeverityBreaking:
    fmt.Print(report.Text())
default:
    err = lock.Write("oascmd.lock.json", next)
}
```

`lock.Decide(policy, report)` returns the write/exit decision if you want the
CLI's semantics without the CLI. `lock.ToModel(entry)` rebuilds a recorded
operation, which is how `additive-only` replays previously generated
commands.

### Runtime verification

Runtime mode can check a **served** spec against a checked-in lock, catching
the case where the live API drifted away from what the CLI was built for:

```go
report, err := oasruntime.VerifyLock(liveSpecBytes, opts, checkedInLock)
if report.Severity().AtLeast(lock.SeverityBreaking) {
    return fmt.Errorf("the API changed under us:\n%s", report.Text())
}
```

Constructor names are ignored on both sides, since runtime mode has none, so
a lock written by the generator can be verified against a live spec directly.

## Why libopenapi

`github.com/pb33f/libopenapi` v0.25.0, over the main alternative
`github.com/getkin/kin-openapi`:

- **Native 3.1 support.** libopenapi models OpenAPI 3.0 **and** 3.1 in one
  high-level model, including 3.1 type unions (`["string","null"]`) and
  JSON-Schema-2020-12 keywords. kin-openapi's data model is 3.0-shaped; 3.1
  documents (which is what the Namefi backend actually serves) are second
  class there.
- **Order preservation.** Paths, operations, properties, and extensions come
  back as ordered maps, so generated command trees and struct fields are
  deterministic without extra sorting on our side — which matters for a
  golden-file test.
- **First-class extensions.** `x-*` values are exposed as `*yaml.Node` on
  every high-level object, which is exactly what the `x-cli-*` handling needs.
- **JSON and YAML** from the same entry point, no format sniffing on our side.

**Go version constraint.** This repo's toolchain is pinned to go1.23.5 and
recent releases of both libraries require newer Go: libopenapi ≥ v0.26.0 and
kin-openapi ≥ v0.136.0 both declare `go >= 1.25`. libopenapi **v0.25.0**
declares `go 1.23.0` and pulls in no `golang.org/x/*` dependencies, so it is
the newest version that builds here — that is the pin. The tradeoff is that
we are a few minor versions behind upstream; bump it when the repo toolchain
moves past 1.25.

## Known limits

- Only `application/json` request bodies are mapped. Other media types (form
  data, multipart uploads) are ignored.
- Header and cookie parameters declared in the spec are not exposed as flags;
  supply them from `ExecOptions.Headers`, `ExecOptions.Cookies`, the `Auth`
  hook, or `OnBeforeExecute`.
- Responses are printed, not decoded. Buildtime mode emits response-shaped
  structs you can unmarshal into yourself, but commands do not do it for you.
- Runtime validation is best effort: required-ness, scalar types, and enums
  are enforced; deeper JSON Schema constraints (`pattern`, `minimum`,
  `oneOf`, nested object validation) are not. `--data` is checked only for
  being syntactically valid JSON.
- `$ref` resolution relies on libopenapi; remote refs behave as libopenapi
  resolves them.
- Command-name collisions (two operations deriving the same path) are not
  detected in runtime mode; in buildtime mode duplicate constructor names get
  a numeric suffix. Use `x-cli-name` or `NameFunc` to disambiguate.

## Build and test

The local toolchain is go1.23.5; run everything with `GOTOOLCHAIN=local`.

```bash
cd projects/oascmd
GOTOOLCHAIN=local go build ./...
GOTOOLCHAIN=local go vet ./...
GOTOOLCHAIN=local gofmt -l .          # must print nothing
GOTOOLCHAIN=local go test ./...
```

Regenerate the golden fixture after an intentional generator change:

```bash
GOTOOLCHAIN=local UPDATE_GOLDEN=1 go test ./gen/
```

Try the example:

```bash
GOTOOLCHAIN=local go run ./examples/petstore --help
GOTOOLCHAIN=local go run ./examples/petstore pets list --help
GOTOOLCHAIN=local go run ./examples/petstore typed pets list --help
GOTOOLCHAIN=local go generate ./examples/petstore    # regenerate the typed tree
```
